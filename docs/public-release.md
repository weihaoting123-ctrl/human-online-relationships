# 隐私与公开发布

## 源码与私人运行区隔离

公开源码和私人运行项目应保留在不同目录。不要把已有聊天目录直接设为公共 Git remote，也不要仅依赖 `.gitignore` 后运行 `git add .`。

本公开基线通过文件白名单复制源码和合成测试；没有复制 `data/`、`reports/`、`backups/`、`vendor/`、`.runtime/`、虚拟环境、`scripts/tmp/`、个人设置、旧 `.git/`、截图和二维码。文档中的个人 home、固定部署位置及实际业务运行计数已泛化。

加密凭据、备份清单、文件名、联系人别名、备注和分析摘要也可能泄露私人信息，不因“不是原话”就允许公开。

## 每次发布检查

1. 只修改公开源码目录；测试必须使用合成数据，不运行个人微信导出。
2. 审阅 `git status --short` 与拟提交 diff；新增文件也要审阅。
3. 审阅新增文件后暂存，运行 `python scripts/check_public_release.py --root .`，同时检查暂存内容和已跟踪文件的工作区内容。此模式不检查未跟踪文件和旧历史；不能替代新增文件审阅。最终仅从已审阅提交生成独立干净发布树，再用 `--tree` 检查全部文件。不要对含 `data/`、虚拟环境或测试缓存的运行目录使用 `--tree`；它会按设计拒绝这些目录。扫描结果只输出文件位置与规则，不打印匹配到的秘密。
4. 运行完整测试，核对 UI、权限、备份/恢复和 AI 范围限制。真实云端调用不是 CI 条件。
5. 复核 README、Issue、PR、Release 和提交作者元数据，不能粘贴本机运行日志、真实截图、账户或私人邮箱。
6. 更新 VERSION、CHANGELOG、里程碑与 Release 清单；只有已经完成且验证的功能进入“已实现”。

扫描只能发现已知形态，不能证明任意自然语言完全匿名。尤其不要把真实聊天改名后当作测试夹具。未来如需演示图，必须从全合成数据生成并单独人工复核后纳入明确白名单。

## 疑似泄露

停止发布，不把可疑原值写进公开 Issue。撤销相关真实凭据，保留本机调查记录；通过 SECURITY.md 的私下渠道反馈。删除工作区文件或新增删除提交不能清除已经公开的 Git 历史、缓存或他人副本。

## 审查边界

这是 AI 辅助的源码与泄露检查，不是渗透测试，不保证发现密码学、时序、运行期或所有依赖漏洞。涉及真实个人信息和生产凭据的部署仍应接受有资质的独立安全审查。公开仓库不代表将本地控制台开放到公网是安全的。
