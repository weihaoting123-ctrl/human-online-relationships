# 1.0.0-rc.5 candidate review · COPILOT-04

The browser assistant now has a visible launch/open button. See [usage](../copilot.md),
[specification](../superpowers/specs/2026-09-24-copilot-launch-button.md) and
[plan](../superpowers/plans/2026-09-24-copilot-launch-button.md).
This is still a release candidate, not formal 1.0 acceptance.

## Boundaries

GET checks only installation files and this project's exact Electron process.
POST requires the existing local session, exact same origin, exact route and
an empty JSON object with checked framing and at most 1024 bytes. It launches
only the fixed installed executable/app and server-owned port, without a shell,
terminal, model configuration lookup, archive read or dependency installation.
Environment flags cannot turn Electron into Node or inject Node options.
Unknown states remain unknown; accepted launch is not proof of window visibility.

Explicit `--show` opens the existing or new assistant in paused settings mode.
It clears the followed target, title candidate and confirmations, stops window
and title workers, and shows only the assistant without stealing focus. Resuming
follow requires an explicit action and does not restore a cloud grant. Ordinary
unflagged launch and second-instance behavior remain non-intrusive. The observed
Windows Electron second-instance argument envelope is accepted only with the
same executable, app path and port; arbitrary/duplicate flags are rejected.

## Independent review and debug

Backend and UI received independent specification and quality reviews. Native
review found an awaiting title refresh could restart its worker after pause;
a red regression reproduced it and a stop-generation fence now prevents it.
A vacuous smoke assertion was replaced by checks against the actual consent
panel, unchecked identity checkbox and disabled confirmation button. No blocking
finding remains after re-review. This is AI-assisted review, not a security audit.

## Controlled deployment

Fourteen explicit runtime/source files were installed after backing up their
previous versions. The private app was patched narrowly: exactly one import,
one GET branch and one POST branch. Independent AST comparison confirmed those
three additions match public source, and removing them restores the complete
previous private AST; unrelated import logic is preserved.

The idle owned server and owned assistant were restarted, not WeChat. Real local
HTTP returned the launch button, then safe status transitioned from stopped to
launch-requested to running. There was exactly one owned visible assistant
window. It was opened using fixed `--show`, in paused settings mode; no real
conversation grant, calibration or model call was initiated. No real chat,
provider configuration, backup or scheduled sync was changed. Installed-runtime
synthetic API regressions and source-hash results are also recorded in the PR.

## Remaining gates

Real WeChat source/model compatibility, quality/cost and mixed-DPI/multiple-monitor
acceptance remain separate. Explicit presentation keeps its captured work area
until reopened; monitor hot-unplug while this settings window is open has not
been tested against the real OS. The installation check verifies presence and
rejects reparse paths; it does not authenticate executable signatures or versions.
No real chats, media, keys, accounts or private runtime configuration are used
as fixtures or published. Starting the assistant never grants analysis permission.
